**Статус: финальный.** Составлен 2026-07-30, ветка `dev`, базовый коммит `5541ba8`.
Решения раздела 2 согласованы с владельцем и являются входными данными, а не предложениями.
Фактическое состояние кода описано в `docs/current-runtime-flow.md`.

Задачи заведены в beads (`bd list`). Этот документ — источник контекста и обоснований;
трекер — источник состояния работ. При расхождении приоритетов верить трекеру.

отдельно. Требования к каждой задаче: изменение поведения фиксируется тестом **до** правки;
`make quality-report` зелёный перед сдачей; один пункт плана = один PR; откат одним revert.
Отклонение от решений Р1–Р12 без согласования недопустимо — если решение выглядит неверным,
задача останавливается и вопрос выносится владельцу.

Цели по приоритету:

1. Понять, что делает код — **сделано**, см. `docs/current-runtime-flow.md`.
2. Устранить ошибки, из-за которых код работает неверно.
3. Уменьшить инфраструктуру.
4. Повысить отказоустойчивость.

## 2. Принятые решения

| № | Решение | Основание |
|---|---|---|
| Р1 | Убрать RabbitMQ. Вебхук пишет событие в inbox-таблицу Postgres, воркер забирает через `FOR UPDATE SKIP LOCKED` | 5 rps; заодно исчезает потеря события при недоступном брокере |
| Р2 | Убрать Redis. Лимитер Teyca — бюджетная таблица в Postgres | единственный потребитель Redis; при одном процессе распределённый лимитер не нужен |
| Р3 | Один воркер-процесс с внутренним расписанием вместо шести | сейчас 8 контейнеров, до 120 потенциальных коннектов к Postgres, 6 heartbeat'ов |
| Р4 | Consent: источник истины — форма регистрации. Список в Listmonk переведён в single opt-in. Бонус начисляется в момент успешного создания подписчика **по событию из CRM**. Опрос Listmonk остаётся только для отписок и блокировок | подтверждение в Listmonk не запрашивается по бизнес-процессу |
| Р4а | Триггером начисления может быть **только событие CRM**. Восстановление маппинга (reconcile, refresh subscriber ids, consistency scan) не должно приводить к начислению — оно ставит `consent_pending`, но не деньги | в июле техническое восстановление маппингов начислило 10 659 бонусов, 94% — старым клиентам, которые ничего не подтверждали |
| Р5 | Бонус за согласие только если email прошёл валидацию и не попал в конфликт. Иначе — `key1 = bad email` без начисления | правило владельца |
| Р6 | Дубли email: уникальный индекс в схеме + детерминированная политика разрешения. `manual_review` остаётся только под технические сбои внешних вызовов | человек в очередь не смотрит, значит правило должно быть полным |
| Р7 | Лимиты Teyca вынести в конфиг и выставить реальные (5/50/500/5000). Склеить вызовы 4 → 2. Не вызывать Teyca, если отправляемое значение не изменилось | причина 429 + защита от мины на 6362 записи |
| Р8 | Reconcile: фазу 2 перевести на батчевые запросы, убрать `break` на всю пачку | до 500 последовательных HTTP к Listmonk каждые 5 минут — самый дорогой участок системы |
| Р9 | `legacy_snapshot_importer` (651 строка) и его раннер удалить — импорт выполнен. Остальные разовые воркеры вынести из `app/` и помечать как сервисные | 6 воркеров не работают в проде, но неотличимы от рабочих |
| Р10 | Начисленные ранее бонусы за автоматическое согласие законны, не отзываются | решение владельца |
| Р11 | Отписки отправляются в Teyca (`key1 = blocked`) задачей в `external_call_outbox` с низким приоритетом под бюджетом вызовов, не синхронно из `consent_sync`. Не ставить задачу повторно, если это значение уже отправляли. **Кратко пересматривалось 2026-07-30** (отказ от отправки вовсе) и **возвращено 2026-07-31** — владелец подтвердил, что консистентность карточки в Teyca нужна | решение владельца: сохранить консистентность данных в Teyca для отписавшихся, не рискуя повторить аварию из раздела 3 (доставка — только под бюджетом из `teyca-sync-3al`) |
| Р12 | Разделить `consent_pending` на два независимых признака: «надо свериться с Listmonk» (техническая потребность) и «клиенту положен бонус» (следствие события CRM) | сейчас это одно поле, и любое техническое восстановление маппинга выглядит как основание для выплаты — см. Р4а и раздел 3 |
| Р13 | **Любые изменения боевой БД — только alembic-миграциями**, включая разовые правки данных (чистка дублей, снятие флагов, backfill). Ручных `UPDATE` в проде нет | решение владельца: версионирование, прогон на копии, откат, след в истории |

**Ловушка Р13:** `CREATE INDEX CONCURRENTLY` не выполняется внутри транзакции, а alembic по
умолчанию оборачивает миграцию в транзакцию. Нужен `op.get_context().autocommit_block()`,
иначе миграция уникальных индексов упадёт. Data-миграции обязаны быть идемпотентными и
выполняться пачками, а не одним оператором на всю таблицу.

### Что подтверждено в API Teyca (файл `teyca-api.json`, версия от 2026-07-30)

- `POST /v1/{token}/passes/{user_id}/bonuses` принимает **массив** `bonus[]` — несколько
  начислений одним запросом.
- `PUT /v1/{token}/passes/{user_id}` принимает произвольный набор полей — `key1` и `key2`
  ставятся одним запросом. Отсюда склейка 4 → 2 вызова на нового клиента.
- `POST /v1/{token}/operations` с фильтром `user_ids[]` — батч-чтение истории операций.
  Использовать для сверки перед разовым доначислением, чтобы не начислить дважды.
- Батч-эндпоинтов на изменение карт **нет**. Сокращать количество вызовов можно только
  склейкой полей и отказом от повторов с тем же значением.

## 3. АВАРИЯ: система деградирует с 2026-07-29

Установлено на восстановленном дампе прода (2026-07-30). Причинно-следственная цепочка:

0. **Предыстория (июль).** Начислено **10 659 consent-бонусов, из них 9973 (94%) —
   клиентам, заведённым до июля** (самый старый — 2025-08-04). Пики: 3018 бонусов 13 июля,
   1742 — 24 июля, 1654 — 12 июля. Это не новые регистрации (их ~33 в сутки), а массовое
   начисление существующей базе. Механизм: восстановление маппингов (reconcile / refresh
   subscriber ids) выставляет `consent_pending = true`, а consent-sync считает согласием
   статус `enabled` — и начисляет. При `CONSENT_BONUS_AMOUNT = 110` это ~1,17 млн бонусов
   за месяц. Бонус выдавался не за согласие клиента, а за техническую операцию с нашей
   стороны.
1. По этой аудитории ушла рассылка, и **6362 подписчика отписались** (35% базы) — сейчас
   они `blocklisted` с непогашенным `consent_pending`. Отписки — подтверждено владельцем.
   Из них 3375 ранее получили consent-бонус.
2. Они попали в дельты, и `consent_sync` начал ставить каждому `key1 = blocked` в Teyca —
   по одному вызову на запись. Замерено по `consent_checked_at`: **2310 «блокирующих»
   касаний 29 июля и 4007 — 30 июля**, при том что до 28 июля их было по одному в день.
3. Суточный лимит Teyca (5000) исчерпан. Лимитер начал отвечать
   `wait_seconds ≈ 70839` (19,7 часа — остаток суточного окна).
4. При ошибке Teyca ветка blocked вызывает `mark_checked(pending=True)`
   (`consent_sync_worker.py:321-330`) — флаг **не снимается**. Watermark не продвигается
   мимо неуспешных (это поведение специально починили в `ef8123f`). В результате каждый
   прогон — раз в минуту — заново долбит ту же пачку из 500 записей. 500 × ~8 прогонов до
   исчерпания лимита = 4000 вызовов в сутки, что и совпадает с замером.
5. Из-за исчерпанного лимита стоит всё остальное: **120 задач
   `teyca_block_invalid_email` висят в `pending` с 30 марта**, `attempts = 0`,
   `last_error = "Teyca rate limiter is busy... wait_seconds=70839"`. У 95 из них у
   пользователя пустой email — то есть отметка «плохой email» в Teyca не выставлена
   четыре месяца.

Это ровно та «мина на 6362 записи», о которой шла речь при планировании, — она сработала.

**Важно про механику цикла.** `consent_sync.run_once` (`:511-547`) идёт по дельтам из
Listmonk и вызывает `_process_pending_user` для каждой смапленной записи **без проверки
`consent_pending`** (`:100-112`). Поэтому правка флага в БД цикл не останавливает: воркер
всё равно перечитает ту же пачку по watermark и снова пойдёт в Teyca. Останавливает только
остановка процесса или правка кода.

Первоочередные действия строго в этом порядке:

| # | Действие | Эффект |
|---|---|---|
| А1 | **Остановить контейнер `consent-sync`** (`docker compose stop consent-sync`) | единственное, что немедленно прекращает трату лимита |
| А2 | ✅ Правка кода (2026-07-31): ветка `blocked` в `consent_sync_worker.py` больше не вызывает Teyca вовсе — отписка фиксируется только локально (`mark_checked`), решение владельца от 2026-07-30 (см. раздел 12) отменяет более раннюю формулировку Р11 про outbox-задачу | цикл физически невозможен: воркер вообще не ходит в Teyca по ветке blocked |
| А3 | Запустить `consent-sync` обратно | воркер за ~13 минут (6362 / 500 записей за прогон) пройдёт всех отписавшихся, снимет `consent_pending`, продвинет watermark |
| А4 | Дождаться сброса суточного окна | лимит освобождается для остальных вызовов (invalid-email диспетчер и т.д.) |
| А5 | Дать диспетчеру разобрать очередь `teyca_block_invalid_email` под бюджетом (~300 вызовов в час) | 120 задач, висящих с марта, уйдут в течение часа-двух после сброса лимита |

Ручная правка `consent_pending` в БД не нужна: после А2 воркер сделает это сам и корректно
продвинет watermark. Меньше ручных записей в прод — меньше риска.

Приоритет в очереди: блокировки невалидных email (120 штук, ждут с марта) должны уйти
раньше 6362 отписок — они старше и влияют на доставляемость.

Пока А2 не сделана, `consent-sync` держать остановленным. Остальная система (приём вебхуков,
consumers, диспетчеры) работает без него.

## 5. План по дублям email

Порядок нельзя менять: индекс нельзя ставить до чистки, политику нельзя писать до замеров.

**Этап 1. Политика разрешения** (детерминированная, без участия человека):

| Случай | Как определяется | Действие |
|---|---|---|
| Один человек, две карты | телефоны совпадают (2 группы из 82) | email остаётся у карты с более свежей активностью, у второй очищается **без** пометки `bad email` |
| Разные люди | телефоны различаются (80 групп) | email остаётся активной карте; второй — очистить email, `key1 = bad email`, начисления нет |
| Не определяется | — | тай-брейк: более свежая активность (`date_last`, при пустом — `updated_at`), при равенстве — меньший `user_id` |

Группы больше двух карт (одна группа на 10 карт, по одной на 5, 4 и 3) обрабатываются тем же
правилом: один победитель, остальные — проигравшие.

**Политика проверена на реальных данных** (симуляция на копии прода 2026-07-30): 82 группы →
82 победителя и 96 проигравших, ровно один победитель на группу, неразрешённых случаев нет.
Тай-брейк по дате понадобится в 47 группах, в 4 группах нет активности ни у одной карты —
там сработает `updated_at`, а затем `user_id`.

**Этап 2. Разовая чистка** 82 групп и 98 висящих `pending` через существующий
`email_repair_backfill`: сначала dry-run, сверка плана, потом применение. Очистить надо 96
email. Расход лимита Teyca — около 100 вызовов, вписывается в одно часовое окно (но только
после А1 из раздела 3, иначе лимита нет).

**Этап 3. Уникальный индекс** на `lower(trim(email))`, только для непустых значений,
создание `CONCURRENTLY`. Проверено на копии прода:

- `listmonk_users` — индекс создаётся **успешно, можно ставить сразу**;
- `users` — падает с `Key (lower(TRIM(BOTH FROM email)))=(123@mail.ru) is duplicated`,
  то есть строго после этапа 2.

После этого конфликт становится ошибкой БД, а не результатом проверки селектом — сейчас
проверка не работает в принципе, потому что блокировка берётся по `user_id`, а конфликтуют
разные `user_id`.

### Что считается «нормальным» email (уточнение к Р5)

Проверка не одна, а четыре уровня с разной природой и разным моментом срабатывания.

| Уровень | Что проверяет | Как реализуется | Когда срабатывает |
|---|---|---|---|
| 1. Синтаксис | форма адреса | существующий `is_valid_email` (`consumers/common.py:104-122`) | в момент обработки события |
| 2. Уникальность | адрес не занят другим `user_id` | уникальный индекс `lower(trim(email))` | при записи в БД |
| 3. Правдоподобность домена | домен вообще существует | MX-запись, кэш **по домену** | при первом появлении домена |
| 4. Реальность ящика | письмо доходит | bounce от Listmonk | асинхронно, после отправки |

Уровень 1 уже есть и проверяет: `trim`, длину ≤ 254, отсутствие пробелов, ровно одну `@`,
непустые local и domain, отсутствие точки в начале и конце local, отсутствие `..`,
local ≤ 64 и совпадение с регулярным выражением. Вызывается из `create_user.py:93` и
`update_user.py:171`.

Чего уровень 1 **не** ловит: несуществующий домен, опечатку (`gmail.con`), мёртвый ящик.
Именно поэтому `123@mail.ru` проходит проверку — синтаксически он безупречен. Такой мусор и
дал группу из 10 карт на один адрес.

Уровень 3 — предложение, требует решения владельца. Он дёшев: адресов 18 тысяч, а доменов
сотни, поэтому кэш держится по домену и DNS-запрос делается один раз на новый домен. Ловит
опечатки и мёртвые домены до того, как по ним уйдёт рассылка.

Уровень 4 — единственный авторитетный, но он приходит уже после отправки. Bounce означает
`key1 = bad email` и очистку адреса. Ранее начисленный бонус не отзывается (Р10).

**Бонус по Р5 начисляется при прохождении уровней 1 и 2** (и 3, если его включат).
Уровень 4 на начисление не влияет ретроспективно.

**Этап 4. Обработка в рантайме.** Конфликт ловится ошибкой уникальности при записи и
разрешается задачей в outbox. Отдельный `email_repair_worker`, который никогда не был в
расписании, исчезает как сущность.

**Этап 5. Видимость.** Алерт на записи `manual_review` старше часа (это теперь только
технические сбои) и на возраст неразрешённых конфликтов.

## 7. План по лимитам Teyca

1. Лимиты в конфиг, значения реальные (правка С1).
2. Склейка вызовов 4 → 2 (см. раздел 5, пункт 3).
3. Отказ от повторной отправки неизменившегося значения (правка С4). Требует хранить
   последнее отправленное значение `key1` / `key2` локально.
4. Замена sliding-window на **бюджет в Postgres**: строка на окно (минута/час/сутки) со
   счётчиком и границей окна. Лимит перестаёт быть блокирующим ожиданием и становится
   размером выборки: воркер забирает из outbox `LIMIT min(batch, остаток бюджета)`.
   Следствия: бюджет переживает рестарты, не зависит от числа процессов, виден обычным
   SQL (можно строить график «сколько осталось на сегодня»), Redis не нужен.
5. Приоритет операций при скудном бюджете: сначала блокировки невалидных email, потом
   бонусы. Сейчас порядок — просто по времени создания.
6. Ожидание при исчерпании суточного бюджета бессмысленно (ждать до полуночи) — задача
   должна откладываться, а не блокировать воркер. Текущее
   `EXTERNAL_DISPATCHER_TEYCA_RATE_LIMIT_MAX_WAIT_SECONDS=0` уже ведёт себя так, поведение
   сохранить.

## 9. Инструменты

Ключевое ограничение: цель — уменьшить инфраструктуру, поэтому новых сервисов не добавляем.

**Берём:** `pydeps` (граф импортов, разово), Mermaid (диаграммы, уже используется),
`semgrep` (один прогон по async-антипаттернам), уже настроенные ruff / basedpyright / bandit /
radon / xenon / vulture / deptry / refurb / pytest+coverage, structlog + Loki (уже есть),
метрики через LogQL поверх существующих логов, `py-spy` (профилирование по требованию),
`k6` (нагрузочный smoke), respx + testcontainers (fault-injection и интеграционные тесты).

**Не берём:** `pyan3` и `snakefood` (не поддерживаются, на Python 3.14 ненадёжны);
PlantUML и D2 (дублируют Mermaid); `pylint` (перекрыт ruff + basedpyright); OpenTelemetry
с Jaeger / Tempo / SigNoz (один сервис не оправдывает трейсинг-бэкенд, `trace_id` в Loki
отвечает на те же вопросы); Prometheus (новый сервис — только если LogQL не хватит);
Locust / wrk / Vegeta (одного k6 достаточно); scalene / cProfile / memray (по факту, если
`py-spy` покажет хотспот); `pytest-mock` (в тестах уже `unittest.mock`).

`trace_id` уже сквозной: генерация в `app/api/webhook.py:153`, `correlation_id` сообщения
(`app/mq/publisher.py:42`), колонка в `external_call_outbox`, привязка через
`structlog.contextvars` в consumer'ах и диспетчере. Пробел: периодические воркеры
генерируют синтетический `trace_id` вида `consent-sync:{user_id}:{subscriber_id}`, не
связанный с исходным событием.

## 10. Слабые места (порядок исправления)

0. **Цикл consent-sync выжирает суточный лимит Teyca — авария, раздел 3.**
1. **Начисление срабатывает от технической операции, а не от согласия клиента:**
   восстановление маппинга ставит `consent_pending`, consent-sync принимает статус
   `enabled` за согласие и платит. В июле так ушло 10 659 бонусов (Р4а).
2. `consent_pending` не снимается при терминальных исходах: 473 записи с уже начисленным
   бонусом и 6362 заблокированных возвращаются в обработку бесконечно.
3. Лимиты Teyca мягче реальных → 429 (правка С1).
4. Условие consent сломано после перехода на single opt-in (С2).
5. Бесконечный requeue: `x-max-delivery-count` выключен по умолчанию (С3).
6. Гонка по email: проверка селектом под блокировкой по `user_id` не защищает (раздел 5).
7. `email_repair_log` без обработчика: 98 записей висят с марта (раздел 5).
8. Дубликаты закрываются как `done` без обновления маппинга (С5).
9. `defer` по rate limit не расходует попытку и не имеет потолка: 120 задач откладываются с
   марта, `attempts` навсегда 0, до `dead` они не дойдут никогда.
10. Зависшие claim'ы в outbox: непойманное исключение оставляет строку в `processing` на 5 минут.
11. Обрыв consistency scan по `break` при первой ошибке Listmonk (фаза 6).
12. Потеря события при недоступном RabbitMQ — inbox-таблицы нет (снимается в фазе 7).
13. Три копии формулы backoff: `run_queue_consumers.py:548`, `:554`,
    `external_call_outbox.py:341`.
14. Мёртвые сущности: `QUEUE_MERGE`, клиенты Listmonk/Teyca в `ConsumersRunner`,
    недостижимая ветка 429 в consumer'е.
15. Heartbeat в файловой системе контейнера — снаружи о живости воркера судить нечем.
